# 驭灵 · 本地二进制信号重映射主路线施工计划

> **版本**：v1.0 · 编制日期：2026-08-20
> **核心目标**：任何平台的二进制文件，在任意其他平台上无差别执行，**不依赖WSL2、不依赖远程节点、不依赖任何外部兼容层**。
> **本计划是唯一主路线**：B0/B1/B2 的所有章节均以此为目标，不以"加速路径""降级方案"替代主路线。


## 一、北极星定义（本计划不可变锚点）

| 维度 | 定义 |
|------|------|
| **最终目标** | 驭灵自身完成跨平台二进制执行——读取ELF/PE/Mach-O，拦截系统调用，转换语义，注入目标平台，回填结果。全过程由驭灵自身完成。 |
| **绝对禁止** | 以WSL2、远程节点、Wine、QEMU、任何外部子系统/兼容层作为"跨平台执行"的最终实现方式。这些可以是实验辅助工具，但**不能作为主路线的交付物**。 |
| **验收标准** | 在没有任何WSL2/远程节点的Windows机器上，执行 `daoti run ./hello.elf`，程序运行成功，输出正确结果。 |


## 二、本地重映射的核心能力拆解

本地重映射不是"一个功能"，是**四个独立能力层的组合**。每一层有明确的输入/输出边界和验收标准，且互不依赖，可以并行开发。

### 能力层 1：格式识别与解析（Format Parser）

| 项目 | 内容 |
|------|------|
| **输入** | 二进制文件路径或字节流 |
| **输出** | 结构化格式描述：文件类型（ELF/PE/Mach-O）、架构（x86_64/ARM64）、入口点地址、段/节表、动态链接信息 |
| **验收** | 读取任意标准ELF/PE/Mach-O文件，输出结构化描述，无解析错误 |
| **当前状态** | PE完整；ELF基础；Mach-O仅magic（<4字节） |
| **本计划需要补全** | Mach-O完整解析：fat/universal header、load commands、LC_SEGMENT_64、LC_DYLD_INFO、code signature、动态库依赖 |
| **不依赖项** | 不需要外部工具、不需要系统调用、不需要WSL2 |

### 能力层 2：系统调用拦截与捕获（Syscall Interceptor）

| 项目 | 内容 |
|------|------|
| **输入** | 目标进程PID或待执行的二进制路径 |
| **输出** | 每次系统调用的事件流：调用号、参数（最多6个）、返回地址、时间戳 |
| **验收** | 在受控环境中（如 `/bin/echo`）捕获完整syscall序列，包含所有参数和返回值 |
| **当前状态** | 仅有抽象接口（`Interceptor` trait），无真实拦截器 |
| **本计划需要补全** | Linux: `ptrace` 或 `seccomp` 事件源；Windows: Debug API 或 ETW；两者都必须是真实进程拦截，不是模拟/构造 |
| **不依赖项** | 不依赖WSL2；不依赖远程节点；不依赖任何外部调试工具 |

### 能力层 3：系统调用语义映射（Syscall Mapper）

| 项目 | 内容 |
|------|------|
| **输入** | 源平台系统调用事件（编号+参数+上下文） |
| **输出** | 目标平台系统调用事件（编号+转换后的参数+上下文） |
| **验收** | 对每个支持的syscall，映射结果在目标平台上可执行且行为等价 |
| **当前状态** | 20条确定性映射（Linux→Win32），已验证逻辑正确，但无真实拦截/注入配套 |
| **本计划需要补全** | 扩展到50条；实现反向映射（Win32→Linux）；为每条映射补充参数转换规则（路径编码、权限标志、句柄语义等） |
| **不依赖项** | 不依赖外部数据库；不依赖网络；不依赖训练数据（B2是增强，不是基础） |

### 能力层 4：系统调用注入与回填（Syscall Injector）

| 项目 | 内容 |
|------|------|
| **输入** | 目标平台系统调用事件（编号+转换后的参数+上下文） |
| **输出** | 目标平台执行结果（返回值、状态变化、副作用） |
| **验收** | 注入的syscall在目标进程中实际执行，结果被正确回填到源进程的内存/寄存器状态中 |
| **当前状态** | 仅有抽象接口（`Injector` trait），无真实注入器 |
| **本计划需要补全** | Windows: `NtContinue` / `SetThreadContext` / `WriteProcessMemory` 组合；Linux: `ptrace` 写寄存器/内存 |
| **不依赖项** | 不依赖WSL2；不依赖远程节点；不依赖任何外部进程管理器 |


## 三、施工顺序（主路线优先级）

以下顺序**不代表"做完一个再做下一个"**，而是**验收依赖关系**——上层依赖下层，所以先做底层，再做上层。

| 顺序 | 层 | 里程碑 | 验收标准 | 预计工作量（AI助手参考） |
|------|----|--------|----------|--------------------------|
| **P0** | **格式解析** | Mach-O完整解析 | `daoti inspect /path/to/macho` 输出完整结构 | 1-2天 |
| **P1** | **拦截器** | Linux ptrace拦截器（最小可用） | 拦截`/bin/echo`的所有syscall并输出事件流 | 2-3天 |
| **P2** | **拦截器** | Windows Debug API拦截器（最小可用） | 拦截`cmd.exe`或任意PE的syscall事件流 | 2-3天 |
| **P3** | **映射器** | 10个基础syscall的Linux→Win32映射（含参数转换） | 映射结果在Windows上可执行且行为等价 | 2-3天 |
| **P4** | **注入器** | Windows注入器（最小可用） | 映射后的syscall在目标进程中真实执行，结果回填 | 2-3天 |
| **P5** | **端到端** | 第一个完整闭环：Linux→Windows本地重映射 | `daoti run ./hello.elf`（静态编译）在Windows上执行成功 | 1-2天 |

**总计**：12-16天（AI全职开发），即可完成"静态编译的ELF程序在Windows上本地执行"的最小闭环。


## 四、精确脚手架（AI助手开发时的目录结构）

以下目录结构是**强制性的**，AI助手不得自行修改或重新组织：

```
crates/daoti-core/src/
├── parser/                    # 【P0】格式解析
│   ├── mod.rs                # 统一导出：parse_binary() → BinaryInfo
│   ├── elf.rs                # ELF解析（已有基础，需补全）
│   ├── pe.rs                 # PE解析（已有）
│   └── macho.rs              # 【新增】Mach-O完整解析（fat header、load commands、LC_SEGMENT_64等）
│
├── interceptor/               # 【P1/P2】系统调用拦截
│   ├── mod.rs                # Interceptor trait（已有）
│   ├── linux.rs              # 【新增】ptrace实现
│   ├── windows.rs            # 【新增】Debug API实现
│   └── event.rs              # SyscallEvent结构体（已有）
│
├── mapper/                    # 【P3】语义映射
│   ├── mod.rs                # Mapper trait + 调度器
│   ├── linux_to_win.rs       # Linux→Win32映射表（已有20条，扩展至50条）
│   ├── win_to_linux.rs       # 【新增】Win32→Linux映射表
│   └── param_convert.rs      # 【新增】参数转换规则（路径、权限、句柄等）
│
├── injector/                  # 【P4】注入与回填
│   ├── mod.rs                # Injector trait（已有）
│   ├── windows.rs            # 【新增】Windows实现（NtContinue/SetThreadContext/WriteProcessMemory）
│   └── linux.rs              # 【新增】Linux实现（ptrace写寄存器/内存）
│
├── engine/                    # 【P5】端到端编排
│   ├── mod.rs                # 【新增】LocalEngine：组装Parser+Interceptor+Mapper+Injector
│   └── local.rs              # 【新增】执行闭环：启动进程→拦截→映射→注入→回填→继续执行
│
└── agent.rs                   # 扩展：run_local() 方法，调用LocalEngine
```


## 五、首轮交付目标（P0-P5合起来等于"第一个闭环"）

**交付物**：在Windows上，不依赖WSL2、不依赖任何虚拟机，运行一个静态编译的Linux ELF程序（如`/bin/echo`或`/bin/ls`的静态版本）。

**用户操作**：
```bash
daoti run ./hello.elf
```

**预期输出**：
```
Hello, World!
exit_code: 0
```

**验收标准**：
1. 运行过程中没有任何WSL2进程启动（`tasklist | grep wsl` 返回空）
2. 运行过程中没有任何远程连接（`netstat -an` 无新增外部连接）
3. 程序的输出（stdout/stderr）与在Linux上原生执行完全一致
4. 程序的退出码与在Linux上原生执行完全一致


## 六、本计划与"快速落地"路线的切割声明

**以下内容不在本计划范围内，AI助手不得擅自纳入主路线开发：**

| 禁止项 | 理由 |
|--------|------|
| ❌ WSL2执行路径（`wsl -d <distro> -- <path>`） | 这是外部兼容层，不是本地重映射。可保留为"实验加速"，但不得作为主路线的交付能力 |
| ❌ 远程执行节点（SSH/gRPC/HTTP远程调用） | 这是分布式调度，不是本地重映射。与本计划完全无关 |
| ❌ B2双梯形网络训练 | 这是实验性增强，不是主路线的基础。在P0-P5完成之前，B2代码必须保持gate默认旁路 |
| ❌ 任何形式的"降级到WSL2"自动回退 | 在本地重映射失败时，应该返回明确错误，而不是自动调用WSL2。WSL2路径应该由用户显式指定（`daoti run --wsl ./hello.elf`）而不是隐式降级 |
| ❌ Mach-O通过远程节点执行 | 北极星是本地重映射。远程节点是另一条产品线，与本计划无关 |

**上述禁止项不得出现在本计划的任何验收标准中。**


## 七、对"AI助手走偏"的强制约束

为了避免AI助手再次走偏，以下约束将写入所有施工计划的"AI助手必读"章节：

1. **本计划中任何提及"WSL2""远程节点""外部兼容层"的地方，都必须标注"非主路线"**，否则AI助手会误以为这些是主路线的组成部分。

2. **本计划的验收标准中，不得包含任何依赖外部兼容层的条件。**

3. **所有"降级"逻辑，必须指向"返回明确错误"而不是"自动调用WSL2"。**

4. **当AI助手遇到"这条路太难"时，必须返回错误信息，而不是绕过它去调用外部工具。**

5. **本计划中的所有"可选的加速路径"都必须由用户显式指定，而非隐式自动触发。**
