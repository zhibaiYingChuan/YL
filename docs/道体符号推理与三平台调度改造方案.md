# 道体符号推理与三平台调度改造方案

## 1. 目标

将 `G:\Yl\daoti` 中的道体 Python 推演资产适配到当前 Rust 项目，形成以下闭环：

```text
Windows / WSL2 / Docker 感知
        ↓
道体符号推理
        ↓
Rust 三平台调度裁决
        ↓
PowerShell / wsl.exe / docker.exe
        ↓
执行结果与二次感知
        ↓
下一轮决策
```

本方案不继续推进动态 ELF 解释器自举调试；动态 ELF 保留为独立能力和真实环境门禁，不得影响三平台调度主链路。

## 2. 当前资产审计

### 2.1 道体核心文件

- `daoti/trigram_space_v16.py`：2048 维状态到 64 卦、八卦、五行、阴阳和相干性输出。
- `daoti/inference_engine_v23.py`：符号因果推演、五行生克、目标卦选择、收敛和推演摘要。
- `daoti/daoti_scheduler.py`：五行气场到推演参数与内部模块权重的调度。
- `daoti/web_ui.py`：旧版 Gradio/FastAPI 展示与推理入口。
- `daoti/train_perception_v2.py`：离线训练脚本，不进入 Rust 运行时主链路。
- `daoti/*.pt`：PyTorch checkpoint，当前不是 Rust 可直接加载的 TorchScript/ONNX 契约。

### 2.2 迁移原则

1. 不逐层翻译完整 PyTorch 网络。
2. 只迁移可验证的符号级输出和确定性规则。
3. Python 负责模型推理时，必须输出版本化 JSON 符号协议。
4. Rust 负责平台能力、调度裁决、安全执行、超时、结果反馈。
5. 不能把规则拟合模型或 JSON 原型模型伪称为原始 `.pt` 神经推理。
6. Python 推理不可用时必须显式降级并记录原因，不得静默伪成功。

## 3. 符号协议

Rust 与 Python 的稳定边界为 `DaotiSymbolicOutput`，至少包含：

```json
{
  "schema_version": 1,
  "model_version": "trigram-v23",
  "gua_name": "坎",
  "gua_index": 28,
  "best_bagua": "坎",
  "wuxing_scores": {"木": 0.12, "火": 0.08, "土": 0.17, "金": 0.21, "水": 0.42},
  "alpha": 0.63,
  "coherence": 0.78,
  "target_gua": "坎",
  "pathway": "stabilize",
  "confidence": 0.86,
  "explanation": "水弱，转入稳定路径",
  "source": "python-daoti"
}
```

边界要求：

- `wuxing_scores` 必须可归一化，缺失字段拒绝进入调度。
- `confidence` 必须在 `[0, 1]`。
- `schema_version` 不匹配时拒绝执行并返回诊断。
- 推理错误、超时、空输出均进入明确降级路径。

## 4. Rust 目标结构

在 `daoti-core` 中新增符号适配模块：

```text
DaotiSymbolicOutput
    ↓
SymbolicDecisionAdapter
    ↓
WuxingHealth / Decision
    ↓
DispatchDecision
```

职责：

- 解析并校验 Python JSON。
- 将五行输出转换为当前 `WuxingHealth`。
- 将符号解释、模型版本、置信度写入决策可观测字段。
- 低置信度、协议错误、服务不可用时回退现有 `RuleEngine`。
- 回退必须产生 warning/事件，不能静默。

## 5. Python 适配层

对 `daoti/web_ui.py` 做兼容改造：

- 保留旧 Web UI 能力。
- 增加仅输出符号 JSON 的推理函数/接口。
- 不让 Rust 依赖 Gradio、Ollama、Qwen 表达层。
- 模型 checkpoint 路径通过环境变量或配置传入，禁止依赖固定 `E:/` 路径。
- 所有模型加载和 API 调用增加超时、异常日志和可观测模型版本。

建议接口：

```text
GET  /api/health
GET  /api/info
POST /api/symbolic/infer
```

`/api/symbolic/infer` 只负责符号推理，不执行平台命令。

## 6. Rust 调度主链路

`CrossPlatformAgent` 的决策优先级：

1. Python 道体符号推理适配器（已配置且协议有效）。
2. 已导出的 `DispatchModel`（本地离线模型）。
3. `RuleEngine`（最终确定性回退）。

所有决策继续经过现有安全执行器：

- Windows：PowerShell
- WSL2：`wsl.exe`
- Docker：`docker.exe`

不引入第三方平台控制工具，不改变北极星目标。

## 7. 执行阶段

### 阶段 A：契约与纯函数

- 新增符号输出结构、校验和适配测试。
- 测试错误 JSON、版本不匹配、低置信度和五行归一化。

### 阶段 B：Python 输出

- 从 `trigram_result` 和 v23 推演摘要生成稳定 JSON。
- 新增 `/api/symbolic/infer`。
- 清理固定绝对路径，支持配置化路径。

### 阶段 C：Rust 接线

- 新增 Python 符号推理客户端。
- 在 Agent 中接入优先级和回退。
- 将模型版本、来源和解释写入事件/报告。

### 阶段 D：端到端验证

- 无 Python 服务：验证明确回退。
- 模拟 Python 服务：验证符号输出进入 `DispatchDecision`。
- WSL2/Docker 可用时验证真实执行；不可用时验证明确诊断。
- 运行 workspace Clippy 和测试。

## 8. 验收标准

必须同时满足：

1. Rust 能解析合法符号输出并生成 `DispatchDecision`。
2. 非法协议不会触发执行。
3. Python 超时/错误会回退且可观测。
4. 三平台执行仍使用原生 PowerShell、`wsl.exe`、`docker.exe`。
5. 现有 workspace 测试无回归。
6. 严格 Clippy 零告警。
7. 至少有一条模拟端到端测试证明：

```text
符号输出 → 五行健康度 → 调度决策 → 执行目标
```

## 9. 非目标

- 不在本阶段将 `.pt` 直接嵌入 Rust。
- 不声称 Rust 已复现完整 PyTorch `forward`。
- 不将动态 ELF 验收结果混入三平台调度验收。
- 不引入第三方 WSL/Docker 控制工具。
