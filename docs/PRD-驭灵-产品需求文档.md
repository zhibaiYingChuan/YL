## 1. 产品定位与核心哲学

### 1.1 一句话定位

**驭灵**是一款面向 Windows + WSL2 + Docker 混合开发环境的「系统气运守护者」——它不只是一个跨平台工具，而是潜伏于系统之中、以东方「观气·调度·归元」哲学统一治理三系统割裂的常驻智能体。

> **核心目标（北极星）**：驭灵最终要实现 Windows / Linux / macOS 三平台任意软件互调——任意平台的二进制文件在任意其他平台无差别执行。上述「环境守护」是**模式A**能力面；**模式B（三平台二进制互调）** 是通往北极星的另一核心能力面，当前以 B0/B1（Linux→Windows）为阶段性起步，macOS 方向在路线图中。

### 1.2 解决的核心痛点

在 Windows + WSL2 + Docker 的混合开发环境中，开发者面临三大「割裂」：

| 痛点 | 表现 | 根源 |
|---|---|---|
| **进程割裂** | Docker Daemon 运行于 WSL2，Windows CLI 无法稳定连接 | 跨系统命名管道不稳定 |
| **文件割裂** | Windows 访问 WSL2 文件（`\\wsl.localhost\`）慢、权限错乱 | 9p 网络协议 + 元数据不兼容 |
| **调度割裂** | 故障时需手动判断「该重启谁」 | 三系统状态无统一观察视角 |

### 1.3 核心哲学：观气、调度、归元

- **观气**（感知）：静默监听三系统的「气」——运行状态、异常信号、资源流动，不打扰用户。
- **调度**（推演与执行）：仅在异常时被唤醒，通过五行生克推演出「当前势态下最佳调度方向」，生成平台自适应指令并安全执行。
- **归元**（收敛与学习）：修复后回归稳定态，并通过在线学习沉淀为「卦原型」，形成可解释的决策轨迹。

### 1.4 角色隐喻

- **道体（帅）**：决策中枢，不执行具体命令，只做「何时、往哪个方向调度」的决策。
- **各平台（将）**：Windows / WSL2 / Docker 执行器，负责把调度指令翻译为平台原生命令。
- **LLM（谋士）**：不确定性检索，当道体推演置信度不足时，从三库（VibeThinker / Qwen / Ornith）检索历史故障案例修正方向。

### 1.5 产品气质

「静水流深」——平时它像空气一样无处不在（无图标、无打扰），遇到跨平台死结时它第一时间现身。任务栏没有它的图标，但每个开发者遇到 Docker 报错时，都会想起它。

## 2. 目标用户与核心场景

### 2.1 目标用户

| 用户画像 | 特征 | 典型诉求 |
|---|---|---|
| **跨平台开发者**（主） | 日常在 VS Code / Windows Terminal 中混用 WSL2 与 Docker Desktop，深受三系统断连困扰 | 一条命令解决问题，不想记忆平台差异 |
| **AI 编程重度用户** | 大量生成代码，环境被反复启动/重建，环境故障频发 | 快速自愈，减少环境排查打断心流 |
| **运维兼开发（DevOps）** | 需要理解「为什么故障」，关注可解释性 | 白话/文言文诊断链，而非日志堆栈 |
| **极客 / 玄学审美爱好者** | 欣赏东方哲学与工具美学的结合 | 视觉化气运仪表盘 |

### 2.2 核心场景（User Story）

**场景 A：Docker 启动不了（水枯）**
> 用户：`daoti heal`  
> 系统：感知到 Docker Daemon 断连 → 推演「坎水动荡，水滞不通」→ 生成指令（重启 WSL 内 daemon → 重启 Windows 服务）→ 安全执行 → 二次感知验证 → 输出「已疏通，耗时 2.3s」。

**场景 B：WSL2 挂起导致 Docker 断连（木滞）**
> 用户：`daoti explain [错误码]`  
> 系统：感知到 WSL 内核挂起 + Docker socket 消失 → 推演「木盛耗水」→ 决策「培木抑盛」（`wsl --shutdown` → 重新拉起 WSL → 启动 docker）→ 输出白话/文言文解释链。

**场景 C：三系统状态总览（观气）**
> 用户：`daoti status`  
> 系统：输出「金（Win）坚、木（WSL）盛、水（Docker）流，三气通畅」，而非裸 CPU/内存数字。

**场景 D：一键快照回魂（归元）**
> 用户：乱装环境导致系统崩溃 → 玄镜中点击「回魂」  
> 系统：按逆序（克→生）逐步回滚到此前保存的三系统快照。

### 2.3 非目标（Out of Scope）

- 不替代 Docker Desktop / WSL 的管理功能本身。
- 不接入云服务；本地知识库离线运行（断网可决策）。
- 首版不做集群 / 多主机调度。

## 3. 三体产品形态详细定义

### 3.1 总览：三体合一

| 形态 | 代号 | 职责 | 技术载体 |
|---|---|---|---|
| **内核** | 道体内核 | 无头守护进程（Headless Daemon），常驻监听、感知、推演、执行 | Rust 常驻二进制 `daoti` |
| **令牌** | 虎符 | 命令行交互，跨终端无感，统一指令 | CLI（同一 Rust 二进制子命令） |
| **玄镜** | 玄镜控制台 | 可视化仪表盘，宏观掌控 + 决策时间轴 + 快照回魂 | Web / 桌面 UI（可选用） |
| **触手** | 触手 | IDE 插件 / 系统右键菜单，极轻量寄生 | VS Code 插件 + 注册表菜单 |

三者共用同一 `daoti` 内核进程：CLI 与 UI 通过本地 RPC/IPC 与守护进程通信。

### 3.2 内核：道体内核（Headless Daemon）——「灵魂」

- **常驻监听**：静默监听三系统关键事件（Windows 服务崩溃日志、WSL 内核挂起信号、Docker Daemon 断连）。
- **本地知识库**：内置压缩「卦原型库」与轻量参数库（CPU 浮点 16 运算），断网环境下独立决策。
- **被动唤醒**：平时只记录「气」的流动；仅在异常时被唤醒进行推演。
- **资源基线**：常驻内存 250MB~400MB（含轻量道体模型），秒级冷启动，单一可执行文件。

### 3.3 令牌：CLI（虎符）——「发号施令」

彻底屏蔽 PowerShell / CMD / Bash 差异。核心指令集：

| 指令 | 说明 | 输出风格 |
|---|---|---|
| `daoti status` | 三系统气运总览 | 五行判词（如「金坚木盛水流」） |
| `daoti heal` | 终极懒人指令：自动诊断 + 修复 + 验证 | 「正在推演…」「已疏通，耗时 2.3s」 |
| `daoti explain [错误码]` | 解释最近一次推演的五行生克过程 | 白话 / 文言文双模式 |
| `daoti run <cmd>` | 跨平台无感执行（自动识别目标平台） | 返回进程 PID |
| `daoti init` | 首次安装：自动探测三系统路径，生成配置 | 适配配置 |
| `daoti snapshot save/restore` | 三系统快照的保存与「回魂」回滚 | 状态摘要 |
| `daoti gui` | 启动玄镜控制台 | — |

**跨平台无感示例**：在 WSL 中输入 `daoti run notepad.exe`，自动识别为 Windows 程序，托管给 Windows 执行器，返回 PID。

### 3.4 玄镜：控制台（UI）——「可视化经络图」

> **技术承载（见 §7.6 技术栈对齐）**：玄镜采用 **Bun + Tauri**。Bun 负责前端构建（React/Vue，极快热重载）与本地 UI 后端服务；Tauri 提供 WebView 壳与 Rust 宿主。玄镜只经 daemon 的 HTTP/SSE 出口**只读**消费 `DaotiEvent`，**不执行任何系统命令**（Bun 红线）。

可选、仅供宏观掌控与美学展示（日常用 CLI）：

- **三环八卦图**：主界面为 Win/WSL/Docker 三环咬合，颜色随「气」强弱实时变化（金白/木青/水黑）。
- **决策时间轴**：竖向「推演链」，记录每次道体干预：
  > `14:03 感知 坎水动荡（Docker 无响应）`  
  > `14:03 推演 水困于土（存储驱动锁死），上卦变艮`  
  > `14:04 执行 释放 Windows 文件句柄，重启 WSL 桥接`  
  > `14:04 结果 水复流通，离火复明（修复成功）`
- **一键快照**：手动创建「三系统快照」（Save State），崩溃时点击「回魂」按逆序（克→生）回滚。

### 3.5 触手：IDE 插件 / 系统右键菜单

- **VS Code 插件**：右键 `.sh` 脚本选择「运行」时，自动判断用 WSL Bash 还是 Windows Git Bash。
- **Windows 右键菜单**：空白处右键「在此处启动道体终端」，自动映射 WSL `/mnt` 路径与 Windows 盘符。

### 3.6 交付物

1. **单一可执行文件**：`daoti`（Windows）/ `daoti`（Linux/WSL），无 Python 环境依赖，扔进 PATH 即用。
2. **一条命令**：`daoti init`。
3. **极简说明书**：一句话——「以后报错，先敲 `daoti heal`，不行再找我。」

## 4. 核心功能需求（Rust 化四层架构）

### 4.1 架构总览

> 原设计方案的 Python 模块已整体迁移至 Rust 工程。架构保持「感知 → 推演 → 调度输出 → 执行」四层，但实现语言、并发模型、接口全部 Rust 化。

```
┌───────────────────────────────────────────────────────────────┐
│                    交互层（CLI / 玄镜 UI / IDE 插件）           │
└──────────────────────────────┬────────────────────────────────┘
                               ▼
┌───────────────────────────────────────────────────────────────┐
│                      感知层 Sensor Layer                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                     │
│  │WinSensor │  │WslSensor │  │DockSensor│  (trait 多态)       │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘                     │
│       └─────────────┴─────────────┘                           │
│                     ▼                                          │
│        StateFusionEncoder  →  2048 维状态向量                   │
└──────────────────────────────┬────────────────────────────────┘
                               ▼
┌───────────────────────────────────────────────────────────────┐
│                    推演层 Inference Engine                     │
│  ┌────────────────────────────────────────────────────────┐   │
│  │ ort(ONNX Runtime) 加载 daoti.onnx（TrigramSpaceV16 推理）│   │
│  │  → 阴阳分叉 → 五行曲率 → 八卦球面 → 河洛折叠             │   │
│  │  → gua_similarity[1,64]                                 │   │
│  └──────────────────────────┬─────────────────────────────┘   │
│                             ▼                                  │
│  CausalAdapter（五行生克因果适配）→ 调度方向 + 不确定性判定      │
│    高不确定 → LLM 三库检索（谋士）                             │
└──────────────────────────────┬────────────────────────────────┘
                               ▼
┌───────────────────────────────────────────────────────────────┐
│                  调度输出层 Action Layer                       │
│  CommandGenerator：{target, command, mode, timeout}[]          │
└──────────────────────────────┬────────────────────────────────┘
                               ▼
┌───────────────────────────────────────────────────────────────┐
│                  执行层 Execution Layer                        │
│  SafeCommandExecutor（白名单/黑名单/防注入）+ trait 执行器      │
└───────────────────────────────────────────────────────────────┘
```

**并发模型**：各层间**禁止共享内存**，统一通过 `tokio::sync::mpsc`（Channel）通信（Actor 模型）；跨线程共享状态用 `Arc<tokio::sync::Mutex<State>>`。见第 7.4 节。

### 4.2 模块清单与接口（Rust 重设计）

原 Python 模块 → Rust 模块映射：

| Python（原） | Rust 模块（新） | 职责 | 关键接口（trait / fn） |
|---|---|---|---|
| `WindowsSensor` | `sensors::windows_sensor` | 采集 Windows 宿主状态 | `impl Sensor` → `async fn collect() -> WinState` |
| `WSLSensor` | `sensors::wsl_sensor` | 通过 `wsl` 桥接采集 WSL2 状态 | `impl Sensor` → `async fn collect() -> WslState` |
| `DockerSensor` | `sensors::docker_sensor` | 自动探测端点采集 Docker 状态 | `impl Sensor` → `async fn collect() -> DockState` |
| `StateFusionEncoder` | `state::fusion_encoder` | 三态融合 → 2048 维向量 | `fn encode(ws, wsl, dc) -> Vec<f32>` |
| `CrossPlatformCausalAdapter` | `causal::causal_adapter` | 卦象 → 三系统调度指令 | `fn interpret(&GuaScore) -> Schedule` |
| `PlatformCommandGenerator` | `command::command_generator` | 生成平台自适应指令 | `fn generate(&Schedule) -> Vec<CommandSpec>` |
| `SafeCommandExecutor` | `executor::safe_executor` | 安全执行 + 回滚 | `async fn execute(&CommandSpec) -> ExecResult` |
| `CrossPlatformAgent` | `agent::daoti_agent` | 对外统一接口（主控） | `async fn diagnose_and_fix() -> FixReport` |

#### 4.2.1 感知层：三系统感知器

统一抽象为 `Sensor` trait（trait 多态，见 7.4）：

```rust
#[async_trait]
trait Sensor {
    type State: Send + Sync;
    async fn collect(&self) -> Result<Self::State, SensorError>;
}
```

- **WindowsSensor**：采集 os 版本、CPU/内存、Docker Desktop 进程、`com.docker.service` 服务状态、WSL 发行版列表、Docker 命名管道 `//./pipe/docker_engine` 是否存在。
- **WSLSensor**：通过 `wsl -d <distro> -- <cmd>` 桥接，采集内核版本、内存占用、dockerd 进程、`/var/run/docker.sock`、containerd、overlay 挂载数、磁盘占用。
- **DockerSensor**：自动探测可用端点（`tcp://localhost:2375` / `unix:///var/run/docker.sock` / `npipe:////./pipe/docker_engine`），采集容器数、镜像数、daemon 版本、磁盘占用；无可用端点时返回 `daemon_unreachable`。

#### 4.2.2 状态融合编码器（StateFusionEncoder）

将三态异构数据融合编码为 2048 维向量，作为推演输入。实现采用「数值特征直填 + 傅里叶特征增强 + 范数归一化（×4.0 对齐语义向量范数）」的确定性方案，不依赖训练，保证可复现。

#### 4.2.3 推演层：道体决策引擎（可选模型 + 降级规则）

推演层拆分为两层：

1. **模型推理（可选）**：`TrigramSpaceV16`（54M 参数）通过 `ort`（ONNX Runtime）加载 `daoti.onnx`，输出 `gua_similarity[1,64]`。作为**独立可选模块**，与主程序解耦。
2. **因果适配（必需）**：`CausalAdapter` 将卦象分数解读为三系统调度建议，内置五行-三系统映射表与调度策略表（见 4.2.4）。

**降级规则引擎（确定性）**：当 `daoti.onnx` 权重缺失、加载失败或 `ort` 不可用时，自动切换为**确定性规则引擎**（Rule Engine），基于传感器布尔/数值状态直接查规则表得出调度方向，保证产品在无模型权重时依然可用。降级判定与切换见第 4.4 节。

#### 4.2.4 五行-三系统映射（核心类比设计）

| 五行 | 映射系统/组件 | 属性 | 生克关系 |
|---|---|---|---|
| **金（决断）** | Windows 宿主机 | 刚性、承载界面、变化慢、权限高 | 金克木（Windows 可关闭/重置 WSL） |
| **木（生发）** | WSL2 内核 | 灵活、生发容器、依赖宿主 | 木生火（WSL 为 Docker 提供基础） |
| **水（流动）** | Docker Daemon | 流动、连接容器、易受干扰 | 水润木（数据反馈 WSL） |
| **火（明察）** | 监控/日志系统 | 明察、提供可见性 | 火生土（日志沉淀为经验） |
| **土（承载）** | 文件/存储系统 | 承载镜像、卷、数据 | 土生金（存储支撑 Windows） |

**三系统主要生克路径**：

```
Windows (金)
   │ 金克木（Windows 可强制关闭 WSL）
   ▼
WSL2 (木) ──木生火──► Docker (水)
   ▲                      │
   └──水润木（Docker 数据反馈 WSL）──┘
```

**故障模式 → 五行状态映射表**（同时用于规则引擎）：

| 故障模式 | 主导五行 | 趋势 | 调度方向 |
|---|---|---|---|
| `docker_daemon_down` | 水 | 衰 | 通水（重启 daemon） |
| `wsl_hung` | 木 | 滞 | 培木（重启 WSL） |
| `windows_pipe_broken` | 金 | 过 | 调金（调整宿主） |
| `disk_full` | 土 | 塞 | 疏土（清理存储） |
| `network_timeout` | 火 | 黯 | 明火（查日志） |

#### 4.2.5 调度输出层：平台自适应指令生成器

`CommandGenerator` 依据调度决策与上下文，展开为平台原生指令模板，输出：

```json
{
  "priority": "wsl2_first",
  "pathway": "restart_daemon",
  "commands": [
    {"target": "wsl2", "cmd": "sudo service docker restart"},
    {"target": "windows", "cmd": "Restart-Service com.docker.service -Force"}
  ],
  "human_explanation": "金旺木衰，火失其母，需先培木"
}
```

每条指令含 `execution_mode`（`sync` / `async` / `fire_and_forget`）与 `timeout`。

#### 4.2.6 执行层：安全执行器 + 回滚

`SafeCommandExecutor` 执行前做安全校验（见第 5 章），执行后支持回滚（针对破坏性命令记录先验状态）。

#### 4.2.7 主控：DaotiAgent

统一对外入口，串联全流程（感知 → 融合编码 → 推演 → 生成指令 → 安全执行 → 二次感知验证 → 记录决策轨迹），并提供 `explain` 与 `snapshot` 能力。

### 4.3 主流程：诊断与修复（Diagnose & Fix）

```
1. 感知    各 Sensor 并行 collect → 三态状态
2. 融合    编码为 2048 维向量
3. 推演    模型/规则 → 卦象分数 → 调度方向 + 置信度
4. 检索    高不确定 → LLM 三库检索修正方向
5. 生成    指令生成器 → CommandSpec[]
6. 执行    SafeCommandExecutor 逐条执行
7. 验证    二次感知，判定是否修复
8. 记录    决策轨迹（时间、卦象、指令、结果）写入本地
```

### 4.4 降级策略（模型不可用时的确定性路径）

| 触发条件 | 降级行为 | 用户可见反馈 |
|---|---|---|
| `daoti.onnx` 缺失 / 加载失败 / `ort` 初始化失败 | 推演层切换为确定性规则引擎（查五行-故障映射表） | 判词标注「规则推演」而非「卦象推演」 |
| 规则引擎也无可匹配故障 | 返回「未识别故障」+ 采集到的原始状态摘要 | 明确告知无法自动决策，建议查日志 |
| 模型存在但置信度低（margin < 阈值） | 触发 LLM 三库检索辅助修正 | 判词标注「参考历史案例」 |

## 5. 安全需求

安全是执行层的**最高优先级约束**。参考原 `SafeCommandExecutor`，在 Rust 中强化实现。

### 5.1 命令白名单

按目标平台定义允许的前缀/命令集合：

| 平台 | 允许命令（白名单） |
|---|---|
| **Windows** | `Get-`、`Set-`、`Restart-`、`Start-`、`Stop-`、`Test-Path`、`wsl`、`docker`、`Write-Host` |
| **WSL2** | `service`、`docker`、`systemctl`、`journalctl`、`pgrep`、`test`、`echo`、`df`、`free`、`mount` |
| **Docker** | `version`、`ps`、`images`、`system`、`restart`、`start`、`stop`、`logs` |

执行时校验命令首部是否命中白名单前缀，未命中即拦截。

### 5.2 命令黑名单（禁止模式）

以下模式**一律拦截**（大小写不敏感匹配）：

- `rm -rf /`、`dd if=`、`mkfs`、`format`
- `shutdown -h`、`del /f /s`
- `Remove-Item -Recurse -Force C:\`
- 所有涉及文件系统格式化、全盘删除、系统关机的破坏性命令

### 5.3 禁止 Shell 注入

- **强制 `shell = false`**：所有命令以参数数组形式执行（`std::process::Command` 或 `tokio::process::Command`），**绝不通过字符串拼接交给 shell 解释**。
- 平台命令通过 `Command::new("powershell").args(["-Command", cmd])` 形式传参，避免注入面。
- 模板参数（如 `{service_name}`、`{container_name}`）在展开前必须通过 `CommandSpec` 白名单校验，不允许出现 shell 元字符（`;` `|` `&` `$` `` ` `` `>` `<` 等）。

### 5.4 执行沙箱与超时

- 每条指令绑定 `timeout`（默认 10s，破坏性/重建命令可放宽至 60s），超时强制终止并返回错误。
- 执行器运行于受限上下文：不继承用户可写环境变量中的危险注入内容；以最小权限运行。

### 5.5 破坏性操作的确认与回滚

- 对 `shutdown`、`prune`、`reset` 等破坏性命令，CLI 需二次确认；玄镜中需显式确认（除非「干预（阳）」模式已开启且策略标记为自动）。
- 执行前记录先验状态（服务状态、socket 存在性等），失败/中断时按逆序回滚。

### 5.6 敏感信息保护

- 日志中禁止明文记录命令参数中的路径密钥、token；脱敏后再写入决策轨迹。

## 6. 非功能需求

### 6.1 性能与资源

| 指标 | 目标值 | 说明 |
|---|---|---|
| 常驻内存 | 250MB ~ 400MB | 含轻量道体模型；比 Docker Desktop 轻一个数量级 |
| 冷启动 | 秒级 | 不初始化 Python 解释器，命令敲下即刻并行采集 |
| 感知时延 | < 2s | 三传感器并行采集 |
| 推演时延 | < 300ms（模型）/ < 10ms（规则） | ONNX 推理由底层 C++ 运行时承担 |
| 修复总时长 | 典型 < 5s | 含执行与二次验证 |
| 单可执行文件 | 1 个二进制 | 无外部运行时依赖 |

### 6.2 可靠性

- **不崩溃**：全程 `anyhow`/`thiserror` 错误传播，`?` 操作符替代 `unwrap`/`expect`（禁用于生产路径）；任何环节错误仅优雅返回，不使守护进程崩溃。
- **断网可用**：本地知识库离线决策，不依赖外部服务。
- **异常路径**：命令超时、进程无响应、socket 消失均需有兜底反馈与状态恢复（详见第 9 章验收中的韧性用例）。

### 6.3 可解释性（核心差异化）

- 每次决策输出**人类可读判词**（白话/文言文双模式）。
- 决策轨迹完整落盘（时间、卦象、指令、结果、置信度）。
- 支持 `daoti explain [错误码]` 回溯推理链。

### 6.4 可扩展性

- 传感器通过 `Sensor` trait 扩展新平台/新维度。
- 维度管理器（DimensionManager）支持未来扩展更多感知维度。
- 推演模型可独立升级（替换 `daoti.onnx`），不触碰主程序。

### 6.5 可测试性

- 感知、推演、调度、执行各层接口隔离，可单测。
- 规则引擎为确定性输入输出，可穷举测试。

## 7. 技术栈裁决说明

### 7.1 裁决结论

**技术栈以 Rust 为主。** 依据：`rust语言开发.md` 明确指出「既然代码由 AI 编写，Rust 是唯一正解」——避开 borrow checker 学习成本，享尽内存安全红利，单一可执行文件，秒级冷启动，250MB~400MB 常驻内存，ONNX 加载权重。本 PRD **采纳该结论作为最终技术栈基线**。

### 7.2 文档取向差异的一致性裁决

| 争议点 | 设计方案.md（Python） | rust语言开发.md（Rust） | 本文裁决 |
|---|---|---|---|
| 主语言 | Python + PyTorch + Gradio + psutil | Rust | **Rust**（采纳 rust语言开发.md） |
| UI 框架 | Gradio | Web/桌面（玄镜） | 玄镜 UI 独立于内核，采用 Web/桌面前端 |
| 系统监控 | psutil | 自实现传感器 | Rust 侧自实现 `Sensor` trait（或复用 sysinfo crate） |
| 模型推理 | PyTorch 运行时 | ort / tch-rs 加载 ONNX | **ort（ONNX Runtime）** |
| 错误处理 | try/except | anyhow + thiserror | **anyhow + thiserror** |
| 并发 | 线程 | Arc<Mutex> + Channel | **Arc<Mutex> + tokio Channel（Actor）** |

**裁决理由**：
1. 产品是「常驻后台、需同时监控三系统」的守护进程，Rust 的内存安全与单二进制交付最契合。
2. AI 编写 Rust 无需支付人类学习曲线成本，却收获编译期消灭竞态/空指针的保障。
3. 感知层用 psutil 的等价物在 Rust 中可用 `sysinfo` 等 crate 实现，不构成采用 Python 的理由。
4. 推演模型由 PyTorch 训练，导出 ONNX 后由 `ort` 加载，保留模型价值同时移除 Python 运行时依赖。

### 7.3 核心依赖清单

| 依赖 | 用途 | 说明 |
|---|---|---|
| `tokio` | 异步运行时、`mpsc` Channel、进程控制 | 全异步 Actor 模型 |
| `ort` | ONNX Runtime 推理 | 加载 `daoti.onnx`，矩阵运算交给底层 C++ |
| `anyhow` / `thiserror` | 错误处理 | `anyhow::Result` + 自定义 `DaotiError` 枚举 |
| `serde` / `serde_json` | 配置与决策轨迹序列化 | JSON 持久化 |
| `clap` | CLI 参数解析 | 实现 `daoti status/heal/explain/...` 子命令 |
| `sysinfo` | 系统资源采集 | 替代 psutil 采集 CPU/内存/进程 |
| `axum` 或 `actix-web` | daemon 对外 HTTP/SSE 事件出口 | Daemon 与玄镜的本地 HTTP/RPC（见 §7.6） |
| `tracing` | 结构化日志 | 关键步骤、错误上下文 |

> **玄镜前端技术栈**：Bun（前端构建 + 本地 UI 后端服务）+ Tauri（WebView 壳 + Rust 宿主）。前端不在 Rust workspace 内，独立于 `daoti-ui-web/` 构建；daemon 侧由 `axum`/`actix-web` 暴露 HTTP/SSE（`/api/events`、`/api/restore`），Bun 只读消费。详见 §7.6。

### 7.4 并发架构（规避 AI 写 Rust 的坑）

- **统一 `Arc<Mutex<State>>`**：所有跨线程共享状态（道体模型、三路传感器状态、配置）包裹为 `Arc<tokio::sync::Mutex<State>>`，避免复杂生命周期标注。
- **Actor 模型**：感知层、推演层、执行层之间**禁止共享内存**，全部通过 `tokio::sync::mpsc` 消息通道通信。
- **trait 多态**：`Sensor`、`PlatformExecutor` 等统一 trait，道体输出 `target` 字段后动态匹配对应的 trait 对象（标准工厂模式）。
- **禁止 `.unwrap()` / `.expect()`**：生产路径一律 `?`。

### 7.5 模块边界（crate 划分建议）

```
daoti/                (workspace)
├── daoti-common/     # 共享错误/事件/配置/日志（最底层）
├── daoti-core/       # 感知/推演/调度/执行 四层核心（无 UI 依赖）
├── daoti-cli/        # CLI 入口（clap）
├── daoti-daemon/     # 常驻守护进程 + HTTP/SSE 事件出口
├── daoti-ui/         # 玄镜 Tauri 宿主（Rust 壳，可选 feature）
└── daoti-ui-web/     # 玄镜前端（Bun/React-Vue，独立于 workspace 构建）
```

> **注**：原建议的 `daoti-models`（ort 模型 + 规则引擎）已并入 `daoti-core::inference`，作为可选 feature 隔离，避免单独 crate 的依赖开销。玄镜前端 `daoti-ui-web` 不在 Rust workspace 内，仅经 daemon HTTP/SSE 出口只读消费。

### 7.6 技术栈对齐（定义者 × 创始者定稿）

> **核心哲学：道体是帅，平台是将，Bun 是旗。** 本 PRD 在第 1 版（纯 Rust 全栈）基础上，按定义者与创始者对齐结论，将玄镜 UI 层落位为 **Bun + Tauri**，并固化 Bun 的职责边界与红线。

**三层职责分工：**

| 层 | 技术 | 职责（Must） | 禁止（Must Not） |
|---|---|---|---|
| **核心层（大脑）** | Rust `daoti-daemon` | 常驻守护、道体推演、安全执行、事件总线唯一数据源 | 不可被 Bun 替代 |
| **令牌层（手脚）** | Rust `daoti-cli` | `status/heal/explain/run/init/snapshot` 全链路，`PlatformExecutor` 统一执行 | 不可用 Bun Shell 执行调度命令 |
| **玄镜层（颜面）** | Bun + Tauri | 玄镜 UI 构建、本地 HTTP/SSE 消费 daemon 事件、三环图/时间轴/快照回魂展示 | 不得自行采集三系统状态、不得执行任何系统命令 |
| **胶水判定** | —— | Bun 的"跨平台"能力用于**展示层一致性**（UI 各平台长得一样） | Bun 的"跨平台"**不得**用于**执行层一致性**（命令安全/可回滚/可审计） |

**Bun 红线（硬性禁止模式）：**
- ❌ 任何 `exec()` / `spawn()` / `$` 模板字符串调用系统命令
- ❌ 任何 `child_process` / `bun:shell` 的导入与使用
- ❌ 任何 `fs` 写入系统关键目录（`/etc`、`C:\Windows` 等）
- ✅ 唯一合法交互：`fetch()` → `http://127.0.0.1:{port}/api/events`（SSE 消费）、`fetch()` → `http://127.0.0.1:{port}/api/restore` 等只读/只传参接口；读取 `daoti.onnx` 权重文件（仅展示模型元信息，不加载推理）

**数据流（R8 单一数据源闭环）：**
- IPC 选 **本地 HTTP + SSE**（daemon 为唯一 producer），弃 Tauri invoke 与命名管道。
- 玄镜 UI **只读** daemon 出口，禁止在 Bun 侧重复采集三系统状态，杜绝第二数据源。

**对 PRD 验收与里程碑的影响：**
- §9.1 F7/F8（玄镜三环图/决策时间轴）：验收时校验前端仅经 daemon HTTP/SSE 出口取数，零系统命令调用。
- §10 P5 玄镜 UI：由纯 Rust Web 调整为 `daoti-ui-web`（Bun）+ `daoti-ui`（Tauri 宿主），其余里程碑不变。

1. **命轮（仪表盘）**：顶部三气归元图（三环咬合，环粗代表负载）；中间互动式五行生克图（金木水三点连线，故障时红克线指向火）；底部近期推演轨迹（最近 3 条）。
2. **推演（诊断链）**：纵向时间线，气柱中轴，左侧卦象图标（䷜坎/䷝离），右侧判词文本；点击可重演推演动画。
3. **归元（设置）**：极简表单；三库（VibeThinker/Qwen/Ornith）显示为并排「镇物」石牌；提供「快照回魂」滑块。

### 8.6 字体与动效

- **字体**：判词 `32px/Bold/0.05em`（霞鹜文楷）；系统指标 `14px/Medium`（Noto Sans SC）；调试日志 `12px/Regular`（JetBrains Mono）。
- **动效**：修复执行时按钮切「罗盘旋转」1~2s（禁骨架屏）；状态切换淡入淡出 300ms / `cubic-bezier(0.25,0.46,0.45,0.94)`；错误非弹窗阻断，右上角赤火符咒光效淡出为顶部横幅。

### 8.7 CLI 输出风格

CLI 判词与五行色彩一致（终端 ANSI 映射）：`status` 输出「金（Win）坚、木（WSL）盛、水（Docker）流」，`heal` 输出「正在推演…/已疏通，耗时 Xs」，`explain` 输出白话/文言文双模式判词。

## 9. 验收标准

### 9.1 功能验收

| # | 验收项 | 通过标准 |
|---|---|---|
| F1 | `daoti status` | 输出三系统五行判词式状态，正确反映各系统在线/断连 |
| F2 | `daoti heal`（Docker 断连场景） | 自动感知→推演→执行→二次验证，输出修复结果与耗时；修复成功判定为 Docker 可连接 |
| F3 | WSL2 挂起场景 | 正确识别「木滞」→ 决策「培木抑盛」→ 执行 WSL 重启 → Docker 恢复连接 |
| F4 | `daoti explain [错误码]` | 输出可回溯的五行生克推理链（白话/文言文） |
| F5 | `daoti run <cmd>` 跨平台 | 自动识别 Windows/WSL 目标，正确托管执行并返回 PID |
| F6 | `daoti snapshot save/restore` | 快照保存与「回魂」按逆序（克→生）回滚到稳定态 |
| F7 | 玄镜三环图 | 三环颜色/粗细随负载实时变化，故障时高亮修复路径 |
| F8 | 决策时间轴 | 完整记录感知/推演/执行/结果四类事件，可点击重演 |

### 9.2 安全验收

| # | 验收项 | 通过标准 |
|---|---|---|
| S1 | 白名单拦截 | 非白名单命令被拦截，返回安全策略错误 |
| S2 | 黑名单拦截 | `rm -rf /`、`Remove-Item -Recurse -Force C:\` 等一律拦截 |
| S3 | 防注入 | 含 shell 元字符的参数无法执行；验证 `shell=false` 生效 |
| S4 | 超时兜底 | 命令超时被强制终止并返回明确错误，进程不崩溃 |
| S5 | 破坏性命令确认 | `shutdown/prune/reset` 在 CLI 需二次确认（除非自动干预已授权） |
| S6 | 回滚 | 执行失败/中断时按逆序回滚先验状态 |

### 9.3 非功能验收

| # | 验收项 | 通过标准 |
|---|---|---|
| N1 | 常驻内存 | 250MB ~ 400MB（含模型），超出需优化 |
| N2 | 冷启动 | `daoti` 命令敲下后 < 1s 进入可交互状态 |
| N3 | 感知时延 | 三传感器并行采集 < 2s |
| N4 | 模型降级 | 删除 `daoti.onnx` 后产品仍可用，走确定性规则引擎并标注「规则推演」 |
| N5 | 断网可用 | 断网环境 `heal` 仍能本地决策 |
| N6 | 可解释性 | 每次决策均有判词 + 决策轨迹落盘 |
| N7 | 异常韧性 | 网络断开、命令超时、进程崩溃场景均有兜底反馈与状态恢复 |

### 9.4 五层交互韧性审计（映射 HCSE 要求）

| 层级 | 范围 | 必测异常路径 |
|---|---|---|
| L1 一级页面 | `status` / 仪表盘 | 加载失败、数据为空、超时 |
| L2 二级弹窗 | 玄镜推演弹窗、确认框 | 打开失败、操作超时、取消中断 |
| L3 三级卡片 | 气运卡片、三库镇物牌 | 内容加载失败、交互无响应 |
| L4 四级嵌套 | 卡片内按钮/表单（回魂滑块） | 嵌套操作超时、状态不恢复 |
| L5 异常全局 | 跨层级异常 | 网络断开、进程崩溃、资源耗尽 |
